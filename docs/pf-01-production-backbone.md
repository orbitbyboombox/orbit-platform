# PF-01 — Production Backbone

## Architecture

The production boundary is additive and preserves the frozen product layers:

```text
Presentation → Application contracts → Domain / Engines
                      ↓
              Infrastructure adapters
             ↙                      ↘
       Supabase repositories       Google Workspace APIs
       PostgreSQL / Storage        Calendar / Drive / Gmail
```

Supabase is authoritative for durable ORBIT data. Google services are outbound mirrors and never overwrite ORBIT. Provider interfaces remain unchanged; production API providers and Supabase repositories are selected only in server-side composition.

## Database and persistence

Migration `database/migrations/0001_production_backbone.sql` creates normalized durable records for customers, projects/services, timeline, assignments, staff, memory, supplies, expenses, profit snapshots, Calendar/Drive synchronization, communications, NOVA conversation state, agreements/evidence, documents, connector jobs, dead letters, connector logs, and audit events.

Mutable aggregates use integer versions for optimistic concurrency and soft deletion where recovery is required. Timeline, agreement evidence, profit snapshots, connector logs, and audit events are append-only. Primary query paths are indexed by customer, project, date, status, and cursor (`created_at`, `id`).

`SupabaseVersionedRepository` provides the shared persistence contract. A version mismatch is a typed conflict, preventing silent lost updates. Connector side effects use unique idempotency keys, retry counters, scheduled retry timestamps, and dead-letter records.

## Authentication and permissions

Supabase Auth remains the identity provider. `profiles` maps `auth.users` to one production role:

- CEO
- Administrator
- Sales
- Operations
- Staff
- Customer
- Readonly

RLS is enabled on every production table. CEO and Administrator receive write authority in the initial migration. Internal roles receive authenticated read access; Staff receives self/assignment access and Customer receives only its own customer/project projection. Fine-grained Sales and Operations mutation policies must be approved against the production responsibility matrix before rollout; service-role access is restricted to server-side jobs.

## Storage

All buckets are private:

- `orbit-documents`: contracts, quotations, generated documents and delivery records.
- `orbit-signatures`: signature images and agreement evidence.
- `orbit-expenses`: original receipts and invoices.

Paths are generated by ORBIT; clients never choose destinations. Downloads use short-lived signed URLs. Database document rows retain checksums and immutable references. Google Drive receives a reference/copy after durable ORBIT storage and never becomes the system of record.

## Realtime and performance

Realtime is prepared for projects, timeline events, assignments, communications, and connector jobs. Consumers must subscribe only to records already authorized by RLS. Lists use cursor pagination; large payloads remain lazy-loaded. Optimistic UI may use entity versions but must reconcile against the persisted row.

## Connectors and recovery

Production provider implementations use Google OAuth access tokens supplied server-side. Tokens are not stored in client state. Calendar supports create/update/cancel/restore, Drive creates deterministic folder structures, and Gmail sends within an existing thread when available. Connector jobs are durable and idempotent; exhausted jobs move to the dead-letter table for operator resolution. Structured JSON logs carry correlation and aggregate identifiers.

## Environment

Required Supabase variables:

```text
SUPABASE_URL
SUPABASE_PUBLISHABLE_KEY
```

Required server-only Google variables:

```text
GOOGLE_WORKSPACE_CLIENT_ID
GOOGLE_WORKSPACE_CLIENT_SECRET
GOOGLE_WORKSPACE_REDIRECT_URI
```

The Google client secret and OAuth refresh tokens must never use `NEXT_PUBLIC_` names.

## Deployment sequence

1. Create a database backup and test project.
2. Apply the migration with Supabase CLI in a staging environment.
3. Create the initial CEO/Admin profile from a controlled server operation.
4. Verify RLS using one account per role, including negative tests.
5. Configure private bucket limits and retention policy.
6. Configure Google OAuth credentials and encrypted refresh-token storage.
7. Run connector idempotency, retry, revoke, and recovery tests.
8. Migrate demonstration records and reconcile counts/checksums.
9. Select production repositories in server-side composition.
10. Cut over only after acceptance and rollback rehearsal.

## Readiness decision

The source-level production foundation is prepared, but remote production is **NO GO** until the migration is applied and validated against an actual Supabase project, the complete role matrix is approved, encrypted OAuth token custody is configured, and all mock composition roots are switched to production repositories. This repository environment has no Supabase administrative connection, so it cannot truthfully certify those external steps.
